## <a id="terms"></a>术语

- **规定**：细化宪法某一条文的一项要求 (`division-of-instructions.rules`)，附有判断它是否被违反的方法。
- **规定源**：存放规定的仓库。本仓是一个；自己编写规定的团队把规定放在自己的规定源里 (见[规定源与引用](#sources-and-references))。
- **规定清单**：一个仓库选用的规定，写成一个列出规定 ID 和规定包的配置文件；它可以继承另一份规定清单。
- **领域 (domain)**：parent 树顶层的节点 (Python、CI、Git、安全等)，只提供一个标题 (见[依赖、one-of 与规定包](#dependencies-one-ofs-and-packs))。
- **one-of**：parent 树上的一种节点，它的子节点至多启用一个；一个都不启用也可以 (见[依赖、one-of 与规定包](#dependencies-one-ofs-and-packs))。
- **锁文件**：写在规定清单旁边；它固定每条启用规定的修订号，并把每个规定源解析到一个确切的提交。
- **检查**：针对一条规定，判断一个仓库、一次变更或一份记录是否合规的代码。
- **审查方**：对检查定不了的情况作出判断的 agent。

## <a id="what-one-rule-holds"></a>一条规定包含什么

一条规定只要求一件事，而且是否违反可以判定：给定一个仓库、一次变更或一份记录，有人能回答「这条规定有没有被违反？」。它就像 linter 里的一条 lint 规则，范围窄到可以检查，这正是 `decidable-provisions` 对每条下位法条文的要求。

它的正文分三部分：要求 (statement)，用一句命令句说该做什么；理由 (reason)；核验方法 (verification)，即怎样判断这条规定有没有被违反。每部分都很短。需要写更多的规定，通常是把几条规定写成了一条，应当拆开。

## <a id="ids-and-revisions"></a>ID 与修订号

规定的 ID 是一个数字，按顺序分配，永不重复使用。预计规定会增长得很快，而且主要由 agent 编写和检查，所以人不会逐条细读；用数字可以免去为起名争论，措辞改变时也从不需要改 ID。领域和 one-of 的 ID 与规定取自同一个序列，所以一个数字在它的规定源里只指一个节点。

规定永不删除。一次修改保不保留 ID，取决于一个问题：它有没有改变什么算合规？

- 没有改变，就原地修改这条规定，修订号加一。改写措辞、增加一个例子、修复检查里的一个 bug：原来合规的仍然合规，原来违反的仍然违反。
- 改变了，修改后的规定就取一个新 ID。旧规定标为被取代，写明取代它的规定，并永久留在规定源里。只有同一规定源的规定才能取代它 (见[规定源与引用](#sources-and-references))。

所以一条规定的 ID 始终代表同一项要求。修订号是每条规定各自的一个数字，从 1 起算；它与宪法的修订号无关。规定的状态是 `draft`、`trial`、`active`、`superseded` 或 `repealed` 之一。宪法还是草案时，每条规定都是 `draft`；`trial` 表示这条规定在定型之前正在实际工作中试用 (见[试行规定](#trial-rules))。撤销而没有替代的规定为废止，它与被取代的规定一样，保留自己的 ID 和文件。

## <a id="rule-file-format"></a>规定文件格式

parent 树上的每个节点 (一条规定、一个 one-of 或一个领域) 是一个 TOML 文件 `rules/<id>.toml`，全部平铺在一个目录里：`rules/42.toml`，不补零，因为 ID 会一直增长，补到几位迟早都不够。树的结构只记在 `parent` 字段里，从不靠目录表达，所以把一条规定挪到另一个 parent 下只改一行，不搬文件。工具一律按数字给文件排序，不按文件名。

一条规定，这里的例子带了中文译文：

```toml
id = 42
slug = "uv-sync-locked-in-ci"
revision = 1
kind = "rule"
status = "trial"
lang = "en"
parent = 7
requires = [12]
authority = ["simplicity"]
constitution = ">=1"
level = "project"
check = "builtin"

[title]
en = "Sync from the lock file first in CI"
zh = "CI 里先按锁文件同步依赖"

[text.statement]
en = "In CI, run `uv sync --locked` before any step that runs Python."
zh = "在 CI 里，先运行 `uv sync --locked`，再运行任何执行 Python 的步骤。"

[text.reason]
en = '''
A job that resolves its dependencies anew can test other versions than the
ones the lock file records, and a stale lock file goes unnoticed.
'''
zh = '''
重新解析依赖的 job 测到的版本可能与锁文件记录的不同，锁文件过期了也发现不了。
'''

[text.verification]
en = '''
Violated when a CI job runs Python before a `uv sync --locked` step, or
runs `uv sync` without `--locked`.
'''
zh = '''
CI 的 job 在 `uv sync --locked` 这一步之前运行了 Python，或者运行 `uv sync` 时没带 `--locked`，即为违反。
'''

[translations]
zh = "<SHA-256 of the original text>"
```

一个 one-of 和一个领域，格式相同：

```toml
id = 5
slug = "python-package-manager"
revision = 1
kind = "one-of"
status = "active"
lang = "en"
parent = 3

[title]
en = "Python package manager"
```

```toml
id = 3
slug = "python"
revision = 1
kind = "domain"
status = "active"
lang = "en"

[title]
en = "Python"
```

各字段：

- `id`：从 1 起的整数，在本规定源的规定、one-of 和领域之间唯一，永不重复使用。文件名就是 ID。
- `slug` (可选)：一个可读的短名，由小写单词以连字符连接，在本规定源内唯一。它只用于网址，以及让人更容易认出这个文件；任何引用都不用它。本仓的规定迁到这个格式时，把原来的文字 ID 放在了这里。
- `revision`：从 1 起的整数，每次原地修改加一 ([ID 与修订号](#ids-and-revisions))。
- `kind`：`rule`、`one-of` 或 `domain`。
- `status`：`draft`、`trial`、`active`、`superseded` 或 `repealed`。
- `superseded-by`：取代这条规定的、同一规定源里的规定的 ID；只在 `status` 为 `superseded` 时出现。
- `lang`：这条规定写成时用的语言，即原文的语言，写成语言代码，如 `"en"` 或 `"zh"`。
- `parent`：父节点的 ID，是同一规定源里的一条规定、一个 one-of 或一个领域。每条规定和每个 one-of 都有 parent；领域没有。
- `requires` (可选)：启用这条规定所需的规定或 one-of。同一规定源里的节点写成数字，别的规定源里的写成字符串：规定源的短名、一个冒号和 ID (`"team:7"`)，短名取自本规定源的 `[sources]` 表 ([规定源与引用](#sources-and-references))。
- `conflicts` (可选)：不能与这条规定一起用的规定，写法同 `requires`，只写在一边 ([依赖、one-of 与规定包](#dependencies-one-ofs-and-packs))。
- `authority`：这条规定所细化的宪法条文的 ID，写法与宪法引用自身时相同，不带命名空间 (`"simplicity"`、`"must-ask.capital"`)。这是字段的值，不是正文里的 `{@...}` 引用，所以 [ID](source-formats.md#ids) 要求规定的引用带命名空间，这一条不适用于它；规定正文里的引用照旧带命名空间 (`{@constitution:simplicity}`)。
- `constitution`：这条规定兼容的宪法修订号，写成 Python 的版本说明符 (`">=1"`、`">=1,<4"`；见[从规定追溯到宪法](#tracing-rules-to-the-constitution))。
- `level`：默认层级，`project` 或 `user` ([规定清单与锁文件](#rule-sets-and-the-lock-file))。
- `check`：怎样检查是否合规 ([检查](#checks))。`builtin`：这条规定在本仓的 crate 里有一个模块。`command`：外部命令，另由两个字段给出，`run` 是命令行，`tools` 是它需要的工具列表 (`["uv"]`)。`review`：没有自动检查，这条规定直接交给审查方。
- `[title]`：简短的标题，只占一行 (多行字符串可以以换行结尾)。
- `[text.statement]`、`[text.reason]` 和 `[text.verification]`：正文的三部分 ([一条规定包含什么](#what-one-rule-holds))。
- `[translations]` (可选)：每种译文语言一个键，原文语言不在其中；值是这份译文所依据的原文的 SHA-256。

领域和 one-of 只有 `id`、`slug`、`revision`、`kind`、`status`、`lang`、`parent` (只有 one-of 有)、`[title]`，以及标题有译文时的 `[translations]`。它们没有正文、检查或别的元数据。

**语言。** 每段文字，即 `[title]` 和正文三部分，都是一张以语言代码为键的表，与[源文件格式](source-formats.md) 相同。`lang` 指明的那种语言必填，其他语言都是可选的译文。所以一条规定可以只用一种语言写，用什么语言写作的人都能直接写。一份译文要给出这种语言的标题和全部三部分，它在 `[translations]` 里的键记下它依据的是哪一版原文。这个哈希值是原文语言的 `title`、`text.statement`、`text.reason`、`text.verification` 四个值按这个顺序、以 TOML 解析器返回的形式 (即构建去掉多行字符串引号旁的换行之前，见[源文件格式](source-formats.md))、把文件里的每个 CRLF 行尾当作 LF (这样无论检出时用哪种行尾，哈希都相同；转义写出的 `\r\n` 不是行尾，原样保留)、用 UTF-8 编码，每两个之间以一个 NUL 字节 (0x00) 连接后的 SHA-256；领域和 one-of 只对标题计算。原文改了、译文的哈希对不上时，检查失败并打印新的哈希值，就像 `check-design-translation` 对设计文档所做的那样。编译成某种语言时，规定有这种语言的译文就用译文，没有就用原文。

## <a id="rule-sets-and-the-lock-file"></a>规定清单与锁文件

规定清单列出规定 ID (以及规定包，见下文)。它的锁文件为每条启用的规定记下所用的修订号，以及它所来自的规定源的提交，所以同一份规定清单和锁文件总是构建出同样的输出。

规定清单是 `statute.toml`，锁文件是 `statute.lock`，都在仓库根目录 (以工具命名，见[工具与第一版](#the-tool-and-the-first-version))。规定清单只列直接选用的规定：

```toml
constitution = { source = "ac", edition = "2026-10" }
rules = ["ac:42", "ac:51"]
packs = ["ac:3"]

[sources]
ac = { git = "github.com/Luolc/agent-constitution", tag = "<tag>" }

[compile]
agents-md = ["statement"]
```

规定清单写明宪法的规定源和版；修订号就是锁文件钉住的那个规定源提交上的修订号，由锁文件记下。`rules` 列出直接选用的规定，`packs` 列出启用的规定包的根，都写成引用 ([规定源与引用](#sources-and-references))。在 one-of 的子节点中选一个，就是把它写进 `rules`，这里是 `ac:51`；没有别的字段管这件事。`rules` 里写了 domain 或 one-of 的，构建失败，并提示 domain 要作为规定包启用，one-of 要通过它的某个子节点启用。`[compile]` 设定编译出的 `AGENTS.md` 收录每条规定的哪些部分：默认只收 `statement`；加上 `reason` 或 `verification`，这些部分也会收进去 ([编译与网站](#compilation-and-the-site))。`[compile]` 里的 `lang` 指定用哪种语言写，默认 `en`。

锁文件是 TOML，由工具写出，从不手改。它记下宪法 (仓库、版、修订号和提交)、每个规定源 (短名、地址和提交)，以及每条启用的规定，不论是直接选用的还是因依赖带进来的 (规定源、ID、修订号和文件的 SHA-256)：

```toml
[constitution]
repository = "github.com/Luolc/agent-constitution"
edition = "2026-10"
revision = "<revision>"
commit = "<commit>"

[[sources]]
name = "ac"
address = "github.com/Luolc/agent-constitution"
commit = "<commit>"

[[rules]]
source = "ac"
id = 42
revision = 1
sha256 = "<SHA-256 of rules/42.toml>"

[[rules]]
source = "ac"
id = 7
revision = 2
sha256 = "<SHA-256 of rules/7.toml>"
```

磁盘上的规定源 (`path`，见[规定源与引用](#sources-and-references)) 没有可记的提交：提交锁文件的那次提交本身就会让它变掉，锁文件就永远不可能是最新的。这时宪法和规定源都按 `path` 记录，不记地址和提交，每条规定的内容只靠它的 `sha256` 钉住：

```toml
[constitution]
path = "."
edition = "2026-10"
revision = "1"

[[sources]]
name = "ac"
path = "."
```

升级是一个明确的步骤：重写锁文件，并显示每条修订号有变动的规定的 diff，以及每条因依赖而带进来或去掉的规定。规定清单启用了被取代的规定时，构建给出警告，并写出它的后继规定。写在 `rules` 里的规定和 `packs` 里的 pack 根，用一条命令 `statute upgrade --replace-superseded` 就能在规定清单里把旧 ID 换成新 ID；由别的规定带进来的，警告会写出是哪条规定把它带进来的。启用了已废止的规定，也给出警告。这些都是警告而不是错误，因为规定清单照旧能用。下游用户不必手动顺着取代链往下找。

「升级之前什么都不会变」这个保证只在锁文件留得住旧版本时成立，也就是按 commit 锁定的 git 规定源。磁盘上的规定源没有旧版本可留：锁文件只记每条规定的 SHA-256，规定一改，算出这个哈希的那份文件就没了。所以 `lock` 按磁盘上的规定源现在的样子读，和 uv 对待 path 依赖一样；`upgrade` 写出同样的锁文件，并显示变了什么。也是因为这个，第一版给不出改动的文字：它只列出宪法的修订号、修订号或内容有变动的每条规定，以及被带进来 (附上原因) 或去掉的每条规定。文字 diff 等 git 规定源实现后再做，那时可以读到旧的 commit。规定的内容变了而修订号没变，`lock` 会给出警告，`upgrade` 会在那条规定的那一行注明，因为规定改了，修订号就要加一 ([ID 与修订号](#ids-and-revisions))。这两处分不出改的是译文还是原文，改了哪个都会提示。

**绑定一部宪法。** 规定清单写明它依据的宪法：来自哪个仓库、哪一版 (edition)、哪个修订号 (revision)。锁文件像固定规定源的提交那样固定这个修订号，一次编译只用一部宪法的一个确切修订号。依据不同宪法的规定清单不会合在一起用：仓库和版至少要一致，修订号则对照每条规定来检查 (见[从规定追溯到宪法](#tracing-rules-to-the-constitution))。宪法修订后，钉在旧修订号上的规定清单不会变；把它移到新修订号上，和别的升级一样是一个明确的步骤。继承了基础规定清单的清单，钉的修订号可以与基础清单不同；这时构建取其中较新的那个，如果有已启用规定的范围容不下它，构建就失败。

**按仓库划分，可以继承。** 规定清单属于一个仓库，它可以继承一份共用的基础规定清单，这样一个用户或团队的所有仓库都认可的规定只写一次。仓库在基础清单之上增加规定、去掉规定，并在 one-of 的子节点中作出选择。这样，当前设计中的法域 (`division-of-instructions.rules`) 就成了一份基础规定清单的所有者，它的各个仓库继承这份清单；每个仓库的规定清单和编译输出，取代每个法域一份的规定选择和编译文件。互斥按规定清单检查，所以一个仓库可以用 uv 管理它的 Python 包，另一个用 Bazel。

**monorepo。** 规定清单可以按路径分成几段，每段指明一个目录和适用于它的规定。互斥在每一段内检查，编译器把每一段的指令文件写进对应的目录，所以 monorepo 的一部分可以用 uv，另一部分用 Bazel。这取决于各个 agent 怎样读取子目录里的指令文件，而这一点各个 agent 不尽相同，这里也还没有测过。实现时要先查的，就是每个支持的 agent 在子目录里工作时会不会读那个子目录的指令文件；查清之后才定下分段的设计。

**放在哪里。** 这套设计仿照 uv 这样的包管理器：规定源相当于包索引，规定清单相当于项目 manifest，锁文件就相当于锁文件，编译相当于 sync，用户级缓存相当于包缓存。仓库里放规定清单、锁文件和编译输出；升级是在仓库里执行的一条命令，结果以一个 pull request 的形式出现。用户级只放工具、规定源的缓存，以及很薄的一层个人设置，存放与人有关、与项目无关的内容：回复用什么语言、把消息当作语音转文字来读、凭证存放在哪里、机器上的目录怎样布局。这一层接管设计中已有的私有 overlay 里与个人相关的那部分。每条规定声明一个默认层级 (项目规定在仓库级，关于人或机器的规定在用户级)，用户可以修改。这样做的原因是：克隆仓库的人、CI 和云端的 agent 都读不到用户级的文件，而且每个仓库固定自己的版本，按自己的节奏升级。第一版只做仓库级 ([工具与第一版](#the-tool-and-the-first-version))。

## <a id="sources-and-references"></a>规定源与引用

一条规定由它的规定源和 ID 确定。提交不属于这个标识的一部分。

**给规定源起名。** 规定清单在 `[sources]` 表里给每个规定源起一个简短的本地名字，并写明地址和要跟随的 tag 或分支：

```toml
[sources]
ac = { git = "github.com/Luolc/agent-constitution", tag = "<tag>" }
team = { git = "example.test/their-team/rules", branch = "main" }
```

规定源也可以是磁盘上的一个目录，`ac = { path = "." }`，路径相对于规定清单所在的目录：自己存放规定的仓库，比如本仓，就这样指向自己。它的规定在该目录下的 `rules/` 里，宪法在 `constitution/<edition>/` 里。第一版只读一个规定源，而且必须在磁盘上；`git` 规定源会报告为暂不支持。

引用写成名字、一个冒号和规定的 ID：`ac:42`、`team:7`。名字只在定义它的文件内有意义，所以两份规定清单可以用 `ac` 指不同的规定源。规定源搬到别的地址时，规定清单改一行，引用一个都不用改。一个规定源如果引用了别的规定源里的规定，它也有自己的 `[sources]` 表，形式相同，其中的名字不必与使用它的任何规定清单一致。构建按地址而不是按名字匹配规定源：一个文件里的 `ac` 和另一个文件里的 `core` 指向同一个地址时，就是同一个规定源。

**版本记在规定源上。** 规定清单写明跟随一个规定源的哪个 tag 或分支；锁文件把它解析到一个确切的提交。这也是 `pyproject.toml` 和 `uv.lock` 的分工：manifest 写明一个范围，锁文件记下确切的版本。引用不带提交，原因有两个。一是升级就得改每一处引用。二是如果同一规定源的两条规定固定在不同的提交上，它们之间的 `requires` 或 `conflicts` 就会指向一条与选用的那条不同的规定。所以一份规定清单对每个规定源只取一个版本。

**跨规定源的依赖。** 一个规定源的规定可以在 `requires` 下列出另一个规定源的规定，例如 `"ac:12"`。这时依赖方所在的规定源要在自己的 `[sources]` 表里声明，它适用于那个规定源的哪些版本，写成一个用 Python 版本说明符表示的范围。编译时，构建为每个规定源寻找一个被所有声明都接受的版本。规定清单自己跟随的 tag 或分支也算作其中一项声明。找不到这样的版本，构建就失败，并指出相互冲突的声明。

**取代只在规定源内部发生。** 只有规定源自己能取代自己的规定。别的规定源不能声明它的规定替代了我们的规定。它可以在自己规定的正文里推荐这个替代；换不换，由用户在自己的规定清单里决定。

**第三方的规定。** 用户可以启用自己选定的规定源里的规定，比如某个团队自己的规定源，或者别人的公开规定源。这是用户的权利，风险也由用户承担：第三方的规定不经过本仓规定的那套审查，却会左右读取编译结果的 agent。内置规定写明，来自本仓之外的规定源的规定和 skill，启用前要怎样检查。默认情况下，用户用默认的宪法和默认的规定清单，不引入任何第三方规定源。引入第三方规定是高级用法，细节以后再写；宪法里不写这些。

**查找公开的规定。** 这件事不需要有人运营一台中心服务器。可以用一个索引仓库列出已知的公开规定源，就像 Homebrew 列出它的 tap 一样，网站上的完整列表也可以从这个索引构建。这一步放在后面做，不属于第一个版本。

## <a id="rules-and-skills"></a>规定与 skill

规定说明必须达到什么状态；skill 说明怎样做到：步骤、模板、命令、已知的坑 (`skills`)。别人能指着说「你违反了这一条」的内容，写进规定；只是帮 agent 把事情做对的内容，写进 skill。

skill 声明自己落实哪些规定，只有当其中至少一条在规定清单里时才安装。仓库的 `AGENTS.md` 只保留这个仓库特有的内容 (它是什么、用什么语言、目录结构、检查命令)，并指明它使用的规定清单 (`division-of-instructions.project-instructions`)。规定清单按仓库选定 ([规定清单与锁文件](#rule-sets-and-the-lock-file))。

## <a id="dependencies-one-ofs-and-packs"></a>依赖、one-of 与规定包

规定之间有两种关系，树上还有另外两种节点：领域和 one-of。

- `parent`：每条规定恰好有一个 parent，它可以是另一条规定、一个 one-of 或一个领域 (见下文)，所以规定构成一棵树，每个领域逐级细化。这棵树决定一条规定在编译出的文本和网站上的位置、它编译进哪个块，以及它属于哪个规定包。
- `requires`：启用规定 A 需要另一条规定 B，或者一个 one-of (见下文)。一条规定可以依赖好几条，这些依赖构成一个有向无环图。一条说明怎样通过 uv 运行检查的规定，依赖让 uv 管理项目依赖的那条规定。也可以依赖另一个规定源的规定；见[规定源与引用](#sources-and-references)。

只有 parent 不够，因为许多规定横跨几个领域：「在 CI 里先运行 `uv sync --locked`」既依赖 uv，也依赖 CI 服务。它放在 uv 那条规定下面，并依赖 one-of「CI 服务」，这个 one-of 的任何一个子节点 (例如一条关于 GitHub Actions 的规定) 都能满足它。

**领域。** 领域是树顶层的节点，例如 Python、CI、Git 或安全。除了 ID 和标题，它只有每个节点都有的那几个字段 ([规定文件格式](#rule-file-format))，没有正文和检查；它没有 parent，也不能单独启用。它下面有任何一条规定启用时，它就作为标题出现在编译输出里。领域不嵌套：更细的分组用领域下面的规定或 one-of。

**one-of。** one-of 是 parent 树上的一种节点，在一份规定清单 (或者它的一个路径分段) 里，它的子节点至多启用一个。一个都不启用也可以，比如完全不用 Python 的仓库；这里的 one-of 从不表示「恰好一个」。Python 下的 one-of「Python 包管理器」有 uv、Poetry 和 Bazel 三个子节点。one-of 有 ID，增加一个 one-of 和增加一条规定一样要经过审查。依赖 one-of 的规定，只要它的任何一个子节点启用，就算满足。

**后来才发现的冲突。** 没人当作备选项的两条规定，可能后来发现不能一起用。怀疑这一点的 agent 报告它，由审查方判断。通常的解决办法是修改规定：拆分、收窄或者改写措辞，保不保留 ID，见[ID 与修订号](#ids-and-revisions)。两条规定都没有问题、只是不能一起用时，在其中一条上写 `conflicts = [ID]`。这个关系是对称的，只写在一边：写在后来的那条上，即发现冲突时正在新增或修改的那条，从不改动早已存在的那条。跨规定源时本来也只能写在自己这边。另一边由工具反推出来，构建检查和网站都在两条规定上显示这个冲突。两边都写了，给一个警告，不算错误。理由是：同一个事实只写在一处 (`no-restating`)，而别的规定源的文件改不了。同一位置上三条或更多互相冲突的规定是备选项，改为收进一个 one-of。一条规定不得声明与这样的规定冲突：启用它时会沿着 `parent` 或 `requires` 直接或间接带进来的规定，因为启用前者就会启用后者；构建遇到这种声明会失败。同一个 parent 下的兄弟规定可以互相冲突。

构建检查下面这些约束：

- 树里和依赖里都没有环。
- 领域没有 parent；每条规定和每个 one-of 都有。
- 规定的 parent 是规定时，算作它的一项依赖：启用一条规定就要求启用它的 parent，parent 不在 `requires` 下重复写。parent 是 one-of 时，这项依赖穿过 one-of，落到 one-of 自己的 parent 上：启用「Python 包管理器」下的 uv，仍然要求启用这个 one-of 上面的那条规定。parent 是领域时不产生依赖。one-of 的某个子节点启用了，就算这个 one-of 启用了。
- 没有多余的依赖：如果 A 依赖 B、B 依赖 C，A 就不再列出 C。
- 跨到另一棵子树的依赖，应当指向一个 one-of，而不是某条具体的规定。这类依赖的数量没有硬性上限；构建会对它们给出警告。
- 在一份规定清单或一个路径分段里，一个 one-of 至多启用一个子节点，启用的规定之间没有冲突。一条规定沿着 `parent` 或 `requires` 会带进同一个 one-of 的两个子节点的，永远无法启用，构建遇到它会失败；依赖一个还没有子节点的 one-of 的规定也一样。
- 一条规定依赖已被取代或已废止的规定时，给出警告，有后继规定的写出后继规定。

**缺的依赖自动补上。** 规定清单启用了一条规定、却没有启用它依赖的某条规定时，工具像包管理器补依赖那样补上缺的那条：规定清单只列直接选用的规定，锁文件记下带进来的规定，升级的 diff 里能看到它们。算作依赖的 parent 也一样处理。在缺依赖的各种情形里，唯一失败的是依赖指向一个 one-of，而规定清单一个子节点都没有启用：工具不能替用户选，于是失败，并列出可选的子节点。

规定包：一个规定包就是一棵子树，以它的根命名，规定清单把根写进 `packs`，就能整个启用它。规定包里的 one-of，规定清单没有为它指定子节点的，和任何一个子节点都没启用的 one-of 一样，不产生任何内容；只有某条启用的规定依赖这个 one-of 时，构建才按上文失败。规定清单在 `rules` 里指定了子节点的，规定包就继续延伸到那个子节点的子树。第一版里，这是进入 one-of 的唯一途径：只因为被某条规定依赖而启用的子节点，不会让规定包延伸到它的子树；作为 one-of 子节点的 one-of，规定包永远进不去。规定包里被取代或已废止的规定不启用，它下面的规定也一样；规定包的根本身被取代或已废止时，这个规定包什么也不启用，构建给出警告，和 `rules` 里写了这样的规定时一样。

## <a id="tracing-rules-to-the-constitution"></a>从规定追溯到宪法

每条规定都在 `authority` 字段里引用它所细化的宪法条文 ([规定文件格式](#rule-file-format))。这个关联双向使用：

- 宪法的某条条文修改时，列出引用它的规定，并开一个任务，逐条检查它们是否仍然适用。
- 在网站上，宪法每条条文下面列出引用它的规定，读者由此看到这条条文在实践中落实成了什么。

**兼容的修订号。** 每条规定在 `constitution` 字段里声明自己兼容的宪法修订号范围，写成 Python 的版本说明符，如 `">=1"` 或 `">=1,<4"`。修订号是整数，所以版本说明符的语法只接受比较整数的那一部分：一个或几个子句，用逗号连接，每个子句是 `>=`、`<=`、`>`、`<`、`==`、`!=` 之一加一个修订号，前后可以有空格。`~=1`、`===1`、`==1.*`、`>=1.0`、单独的 `1`、空串和末尾多一个逗号都报错。最低修订号一般都写。最高修订号只在确知这条规定与更高的修订号不兼容时才写，比如宪法废除了这条规定所依赖的内容；不预防性地写上限，Python 打包生态对依赖上限的经验就是如此。宪法的某一条文被修订时，上面列出的那些规定逐条判断：仍然适用的不动；不再适用的加上限，或者在改动影响了怎样才算合规时改写并开新 ID ([ID 与修订号](#ids-and-revisions))。编译时，规定清单钉住的修订号必须落在每条已启用规定的范围内；否则构建失败，并指出是哪条规定、它的范围是什么。

## <a id="checks"></a>检查

编写检查不用任何专门的语言，声明式的也不用。一小组内置的检查原语 (「这个文件存在」「这个 TOML 文件里这个键是这个值」) 会不断需要再加一种情况、再加「或」、再加「除非」，直到它自己成了一门没人读得顺的语言。检查就是代码，分两种，没有第三种。

**我们的规定：Rust。** 本仓规定的检查放在工具的 crate 里 ([工具与第一版](#the-tool-and-the-first-version))，每条规定一个模块，以规定的 ID 命名 (规定 42 的模块是 `r42.rs`)，就像 ruff 和 clippy 把每条 lint 实现为一个函数。规定的正文和元数据留在 `rules/42.toml`，写规定的人和写检查的人各改各的文件；模块的测试用例跟着检查放在 crate 里。常用的操作，例如从 TOML 文件读一个键，是同一个 crate 里普通的辅助函数；一个操作第三次重复时才抽成辅助函数，不提前 (`simplicity`)。这个 crate 构建成一个二进制文件，随规定一起发布，所以下游用户装一个二进制文件就有了全部检查，不用部署任何脚本。

一条规定被取代时，它的后继规定得到一个新模块，从旧模块复制过来，按需修改。旧模块留在代码里，标为被取代，除非专门要求，否则不运行。

**下游编写的规定：外部命令。** 存放在别的规定源里的规定，把它的检查声明为一条命令 (`check = "command"`，另写 `run` 和 `tools`)，用什么语言都可以。脚本放在那个规定源自己的仓库里，用它自己的工具链运行；规定写明它需要的工具 (例如 uv 或 Go)。约定如下：

- 退出码 0：满足规定；1：违反规定；其他任何值：检查无法判定；
- 标准输出：JSON，为每一处发现给出位置和原因，写成对象 `{"location": ..., "reason": ...}` 的列表。

命令在规定清单所在的目录里用 `sh -c` 运行；检查一个变更时，`STATUTE_BASE` 里是变更起点的 git ref。`tools` 里的工具不在 `PATH` 上、命令 10 分钟后还没退出或还没关闭输出 (它启动的进程一并停掉)、输出超过 1 MiB、退出码为 1 但输出不是上述列表，都算无法判定。

允许规定没有自动检查 (`check = "review"`)；这样的规定直接交给审查方 (见下文)。

## <a id="outcomes-and-the-review-loop"></a>结果与审查回路

检查有三种结果：通过、违反和无法判定。缺工具、超时和脚本崩溃都算无法判定，从不算违反，所以缺了某个工具链不会让检查变红。

自动检查先运行，因为它们成本最低。然后审查方查看违反的结果、无法判定的结果，以及没有自动检查的规定。交给审查方的材料里有每条规定的理由和核验方法，这两部分编译出的 `AGENTS.md` 默认不收 ([编译与网站](#compilation-and-the-site))。是由一个审查方全部接手，还是由几个审查方各接一组，以及怎样分组，在规定清单里设定。

第一版里，`statute check` 运行仓库里已启用规定的检查；带 `--base <ref>` 时，检查变更 `git diff <ref>...HEAD`。它每条规定输出一行，写明结果 (`pass`、`violation`、`inconclusive`，没有自动检查的规定写 `review`) 和一句说明，发现列在下面；然后为审查方列出每条无法判定或待审规定的理由和核验方法。有规定被违反时退出码为 1，否则为 0。内置检查只覆盖规定的一部分时，什么也没发现也算无法判定，不算通过，因为规定的其余部分仍要审查方看：

- 规定 46 (instruction-files-apart) 用与 `check-instruction-changes` 相同的路径表区分指令文件、生成文件和其他文件，变更里既有指令文件又有其他文件的即为违反；路径表没有列出的 agent 工具的文件、路径表以外的指令源文件，以及仓库在自己的 `AGENTS.md` 里声明的路径，交给审查方；没有 `--base` 就没有可检查的变更。
- 规定 43 (credential-designated-place) 带 `--redact` 运行机器上的 gitleaks，扫描变更里的提交或全部历史，有命中即为违反，命中只显示位置和 gitleaks 的规则名；gitleaks 识别不出的凭证，以及仓库以外的地方，交给审查方；没有 gitleaks 时算无法判定。

这两条取代的规定 3 和 7 保留各自的模块，只在规定清单仍然启用它们时运行。

对交给它的每条规定，审查方判断规定是满足还是违反。违反的要修正。审查方的判断与检查的结论不同时，就是检查错了：

- 误报：检查标记了一处其实满足规定的内容；
- 漏报：检查放过了一处违反规定的内容，是在审查别的结果或在后来的工作中发现的。

两种情况都会引出一项提案：修正这条规定的检查。修正检查不改变什么算合规，所以这条规定保留 ID，修订号加一 (`wrong-checkers.fixing`)。人和 agent 都可以依照 `rule-evolution` 提出修改规定。规定就是这样自我改进的：成本低的检查先跑，agent 只看检查定不了的部分，agent 得出的结论再回到检查里。

**谁来判断。** 编译、升级、判断冲突和兼容范围，凡是脚本能判定的，都由确定性的脚本完成。脚本判断不了的，交给 agent，走上面的三种结果和审查回路。这些判断不需要人参与；只有宪法本来就要求人批准的地方，人才出现。这与 `automation-first.decide-and-do` 一致。

## <a id="trial-rules"></a>试行规定

agent 做某项工作时，发现没有任何规定、skill 或惯例覆盖它，就开始把惯例写下来。第一个版本是试行规定 (`status = "trial"`)：用在实际工作中，试行期间可以随意修改，定型之后成为正式规定。本仓自己的规定、skill 和惯例，也打算按同样的方式产生。

**转正。** 这由 agent 决定，不需要人。试行规定在实际工作中用过若干次 (第一版定为 5 次)，其间没有未解决的误报，就由审查方 agent 把它的 `status` 改为 `active`。这只改状态，不改什么算合规，所以原地修改，修订号加一 ([ID 与修订号](#ids-and-revisions))。

## <a id="compilation-and-the-site"></a>编译与网站

**在本地**，编译器读取宪法 (agent 版) 和一份规定清单及其锁文件，写出：

- 一份 `AGENTS.md`，开头写明它依据的宪法的仓库、版和修订号，然后是启用的规定，沿着 parent 树放在嵌套的块里，树每深一层，标题就降一级，下面有启用规定的每个领域是最上一级标题；根没有启用的子树 (对 one-of 来说：它的子节点一个都没有启用) 不产生任何内容，因为没有它，其中的规定一条也启用不了；跨子树的依赖渲染成一个链接。默认每条规定只收它的要求，让文件尽量小；规定清单可以加上理由或核验方法 ([规定清单与锁文件](#rule-sets-and-the-lock-file))，审查方则无论如何都会拿到它们。文件暂时不拆。等用它的某个仓库编译出的文件用 `count-tokens` 量过之后，再按量出的长度定一个阈值，超过阈值的文件沿领域拆开；
- 启用的规定需要的 skill 目录；
- 要安装的检查二进制文件的版本，以及启用规定的外部命令；
- 运行检查的钩子配置。

第一版只写 `AGENTS.md`：`statute compile` 把它写在 `statute.toml` 旁边，用 `--output` 可以写到别的文件；锁文件必须与 `statute lock` 此刻会写出的内容一致，否则不写。它只替换自己写出的文件，即第一行是它那行「文件是生成的」注释的文件；手写的文件原样保留，命令失败。文件依次包含：一行说明文件是生成的注释；一行写明宪法的版、修订号和规定源；规定清单所用语言的宪法 agent 版，即宪法构建写出的 `constitution/<edition>/generated/constitution.<lang>.agent.md`，原样收入；最后是标题「规定」及启用的规定。每个 domain 是二级标题，树每深一层标题降一级，到六级为止，更深的层级停在六级；一个子节点都没启用的 one-of 不出现。节点的标题是它的标题和 ID，前面放锚点 `rule-<id>`，这个锚点只在一个规定源内唯一。依赖另一个 domain 下的节点时，写一行「依赖：」并链接到那个锚点；同一 domain 内的依赖不写出来。规定有该语言的译文就用译文，没有就用原文。规定正文里的引用会渲染出来 ([ID](source-formats.md#ids))：`{@rule:<id>}` 写成被引节点的标题，与它的标题行一样选语言，节点在文件里就链接到它的锚点，不在就在后面加「(规定 <id>)」；`{@constitution:<id>}` 写成该条款在这种语言里的标签，与 agent 版一样是纯文本，例如 `第四条第一款第二项`。标签按这一版宪法的源算出：条和款的编号取自文件名，项的编号取自 `number`，算法与宪法构建相同 ([编译](compilation.md))；与宪法构建不同的是，连着的几处引用不缩写 (`第四条第一款、第四条第二款`)。引用了不存在的节点或条款时命令失败，并指出是哪条规定的哪一部分。规定文件和锁文件里的哈希都不变。skill 目录、检查二进制的版本和 hook 配置暂时还不写。

编译、检查和升级规定清单由同一个命令行工具完成 ([工具与第一版](#the-tool-and-the-first-version))。宪法的编译器暂时仍用 Python ([编译](compilation.md))，以后再并入那个工具。

**公开网站**列出每条没有被取代的规定，让人们能从完整列表里挑选。它的「规定」一栏是列表，按 parent 树排序，每页固定条数 ([静态网站](static-site.md))，每条只显示要求，太长的截断。每条规定有自己的详情页，放它的理由和核验方法、它的检查、它的依赖和冲突 (每个冲突的两边都显示)、它引用的宪法条文，以及它的全部元数据。被取代的规定保留自己的页面，指向它的链接仍然有效，但默认不出现在列表里。

## <a id="the-tool-and-the-first-version"></a>工具与第一版

**工具。** 规定体系的工具用 Rust 写 (见[为什么用 Rust](#why-rust))，在 `crates/statute` 这个 crate 里逐步实现 ([文件结构](file-structure.md))。第一版就是这一个 crate。`statute` 这个名字已经用一个占位版本在 crates.io 上占住 ([发布与版本](amendments-and-releases.md#releases-and-versions))；第一次正式发布前仍可能改名，改了就要用新名字另行发布。规定清单是 `statute.toml`，锁文件是 `statute.lock`，命令有：

- `init`：写一份新的规定清单；
- `add` 和 `remove`：在规定清单里启用一条规定或去掉它，并更新锁文件；
- `lock`：把规定清单解析成锁文件；
- `compile`：写出编译输出 ([编译与网站](#compilation-and-the-site))；
- `check`：运行启用规定的检查 ([检查](#checks))；
- `upgrade`：把规定源和宪法移到更新的版本 ([规定清单与锁文件](#rule-sets-and-the-lock-file))；
- `explain`：说明一条规定为什么被启用、哪些规定依赖它。

**第一版**只做仓库级。用户级是第二步，它的指令文件在用户的家目录里，目前由私有 overlay 安装。本仓的规定已经迁到新格式，每条把原来的文字 ID 留作 `slug`。最先用新格式写的规定里，有关于怎样写设计文档的那几条，正好拿实际工作把整套流程试一遍。

**目前已实现**：`init`、`lock`、`explain`、`add`、`remove`、`upgrade`、`compile` (只写 `AGENTS.md`) 和 `check` (内置检查有规定 43 和 46，以及被它们取代的 3 和 7) 八个命令，只支持一个磁盘上的规定源。继承规定清单和按路径分段都还没有实现；git 规定源、多个规定源，以及在 `requires` 或 `conflicts` 里对别的规定源的引用 (`"team:7"`)，会报告为暂不支持。

**`init`** 在当前目录写一份 `statute.toml`：宪法取自哪个规定源、哪一版，空的 `rules`，以及一个名为 `ac` 的磁盘规定源。`--source <dir>` 指定规定源的目录，相对于当前目录，默认是 `.`。`--edition` 指定哪一版；不给时，`init` 取规定源 `constitution/` 下唯一一个含 `index.toml` 的目录，一个都没有或多于一个时报错，并列出找到的那些。写之前它先解析一遍这份规定清单，解析失败就什么都不写。它不写 `statute.lock`：没有启用任何规定，也就没有要锁定的东西；第一次 `add` 会写出锁文件，已有的 `statute.lock` 会被替换。已有 `statute.toml` 时原样保留，`init` 以退出码 1 退出。

**`upgrade`** 把解析结果与 `statute.lock` 比较，打印变了什么 ([规定清单与锁文件](#rule-sets-and-the-lock-file))，没有变化就说锁文件已是最新，然后像 `lock` 一样写锁文件。没有 `statute.lock` 时没有可比的东西，以退出码 1 退出。加上 `--replace-superseded` 时，它先在 `rules` 和 `packs` 里把每条被取代的规定换成它的后继规定，顺着取代链找到最后一条，文件其余部分保持原样；后继规定已经列出的，只去掉旧的那一项。已废止的规定留给用户自己去掉。改过的规定清单解析不通过时，两个文件都不改。

**切换。** 目前 agent 读的是私有 overlay 的用户级指令文件。这些文件将加一条：仓库里有 `statute.lock` 的，以这个仓库的编译输出为准，用户级指令文件不再适用。先在本仓试行。要等编译输出覆盖了那些文件现在管的最要紧的内容，即凭证、git 流程和审查，才切换。在那之前，编译输出照常构建、用来对比，但不代替它们给 agent 读。

## <a id="why-rust"></a>为什么用 Rust

速度不是主要原因。几百次文件检查和正则表达式匹配，用 Python 也只要一两秒；真正花时间和钱的是审查方调用模型。选 Rust 的原因是：

- 检查作为一个二进制文件发布，不需要 Python 或别的运行时，所以用任何语言的下游仓库都能用；
- 并行运行检查更容易写对；
- [limae](https://github.com/Luolc/limae) 是一个以 Python wheel 发布、从 pre-commit 运行的 Rust linter，已经通过这种方式用到了下游仓库，所以这条分发途径已经试过。

## <a id="what-this-replaces"></a>它将取代什么

[规定文件格式](#rule-file-format) 已经实现，[ID](source-formats.md#ids)、[源文件格式](source-formats.md) 和[规定](rules.md#rules) 现在描述的就是这种格式的规定。本设计的其余部分实现之后，会取代当前设计的另一些部分。那些部分现在不改；等实现本设计的工作合入时再改。

- [选用规定](rules.md#choosing-rules)：带锁文件、在其中列出规定 (按 ID 或规定包) 的规定清单，取代「默认使用全部通用规定，再点名排除」。规定清单属于一个仓库，可以继承一份基础规定清单，由后者接管法域的那部分职能。每份规定清单还写明它依据的宪法 (见[规定清单与锁文件](#rule-sets-and-the-lock-file))。
- [放宽声明](rules.md#relaxation-declarations)：规定清单不用某条规定，或者在 one-of 里选了另一个子节点，都不需要放宽。`adjustable` 的值和 `relaxes:` 声明是否保持原样，在实现本设计时决定。
- [概览](overview.md)：「每个法域自己选用哪些通用规定」这项目标和私有 overlay 选用规定的职责，移到每个仓库的规定清单 (连同继承的基础清单)，overlay 的 apply 步骤变成编译命令；overlay 保留与个人相关的部分和它自己的规定。
- [Skill](skills.md)：skill 声明自己落实的规定，只有其中某条被启用时才安装。
- [编译](compilation.md)：输出增加 skill 目录、检查和钩子配置，编译出的文件开头写明它依据的宪法的仓库、版和修订号，规定沿着 parent 树分组，而不是按第一个 `authority` 所在的条分组。
- [检查程序](checkers.md#checkers)：增加由 Rust 二进制文件运行的规定检查及其三种结果；本仓源文件现有的检查程序保留。
