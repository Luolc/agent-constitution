# 规定清单、引用与依赖

这是[规定体系](rule-system.md) 的一部分，那里的状态和术语也适用于这里。

## <a id="rule-sets-and-the-lock-file"></a>规定清单与锁文件

规定清单列出规定 ID (以及规定包，见下文)。它的锁文件为每条启用的规定记下所用的修订号，以及它所来自的规定源的提交，所以同一份规定清单和锁文件总是构建出同样的输出。

规定清单是 `statute.toml`，锁文件是 `statute.lock`，都在仓库根目录 (以命令命名，见[命令与第一版](statute-command.md#the-command-and-the-first-version))。规定清单只列直接选用的规定：

```toml
constitution = { source = "R", edition = "2026-10" }
rules = ["R42", "R51", "12"]
packs = ["R3"]

[sources]
R = { git = "https://github.com/Luolc/agent-constitution", tag = "<tag>" }

[compile]
agents-md = ["statement"]
```

规定清单写明宪法的规定源和版；修订号就是锁文件钉住的那个规定源提交上的修订号，由锁文件记下。`rules` 列出直接选用的规定，`packs` 列出启用的规定包的根，都写成引用 ([规定源与引用](#sources-and-references))：这里 `R42` 和 `R51` 是第一方规定，`12` 是仓库自己的规定。在 one-of 的子节点中选一个，就是把它写进 `rules`，这里是 `R51`；没有别的字段管这件事。`rules` 里写了 domain 或 one-of 的，构建失败，并提示 domain 要作为规定包启用，one-of 要通过它的某个子节点启用。`[compile]` 设定编译出的 `AGENTS.md` 收录每条规定的哪些部分：默认只收 `statement`；加上 `reason` 或 `verification`，这些部分也会收进去 ([编译与网站](statute-command.md#compilation-and-the-site))。`[compile]` 里的 `lang` 指定用哪种语言写，默认 `en`。

[规定源](rule-sources.md) 加了几个字段。顶层的 `public` 必填，写明仓库是否公开；`R` 以外的每个规定源也为自己写明 `public`，还可以写 `scope`，默认 `"global"`，也可以是 `"local"` (见[四类规定源](rule-sources.md#four-kinds-of-source))。公开仓库把私有规定源写在 `statute.private.toml` 里，这个文件被 git 忽略，用 `base = "statute.toml"` 继承 `statute.toml`，有自己的锁文件 `statute.private.lock`。它编译成 `.statute/AGENTS.full.md`，公开规定与私有规定合在一份里 (见[公开仓库里的私有规定](rule-sources.md#private-rules-in-a-public-repository))。[规定配置](rule-config.md) 又加了本地规定的目录、参数和默认开关，都还没有实现。

锁文件是 TOML，由 statute 写出，从不手改。它记下宪法 (仓库、版、修订号和提交)、每个规定源 (短名、地址、跟踪的分支或 tag、提交，以及 `R` 以外的 `public`；见 [git 规定源](global-configuration.md#git-sources))，以及每条启用的规定，不论是直接选用的还是因依赖带进来的 (它的引用，写法与规定清单相同，如 `R42` 或 `team:7`，本地规定写成 `L12`；它的修订号；文件的 SHA-256；以及去掉译文之后的规定的 SHA-256，只改译文时它不变)：

```toml
[constitution]
git = "https://github.com/Luolc/agent-constitution"
edition = "2026-10"
revision = "<revision>"
commit = "<commit>"

[[sources]]
name = "R"
git = "https://github.com/Luolc/agent-constitution"
tag = "<tag>"
commit = "<commit>"

[[rules]]
rule = "R7"
revision = 2
sha256 = "<SHA-256 of rules/7.toml>"
original-sha256 = "<SHA-256 of rule 7 without its translations>"

[[rules]]
rule = "R42"
revision = 1
sha256 = "<SHA-256 of rules/42.toml>"
original-sha256 = "<SHA-256 of rule 42 without its translations>"
```

规定只用一个字段 `rule` 来写，写法与别处相同，不再拆成规定源和 ID 两个字段，这样按规定清单和提示信息里的写法就能在锁文件里搜到那一行。旧格式的锁文件用 `source` 和 `id` 两个字段写规定，`upgrade` 遇到它会报错，提示运行 `statute lock` 重新写一份。被某条启用的规定覆盖的规定仍保留它那一行，多一个字段 `overridden-by = "L3"`，写明直接覆盖它的是哪条规定 (在一条覆盖链上就是下一环)，这样 `upgrade` 仍会显示它的修改 (见[覆盖](rule-sources.md#overrides))。只因覆盖才带进来、别的都没有启用它的规定，也有自己的一行。

磁盘上的规定源 (`path`，见[规定源与引用](#sources-and-references)) 没有可记的提交：提交锁文件的那次提交本身就会让它变掉，锁文件就永远不可能是最新的。这时宪法和规定源都按 `path` 记录，不记地址和提交，每条规定的内容只靠它的 `sha256` 钉住：

```toml
[constitution]
path = "."
edition = "2026-10"
revision = "1"

[[sources]]
name = "R"
path = "."
```

升级是一个明确的步骤：重写锁文件，并显示每条修订号有变动的规定的 diff，以及每条因依赖而带进来或去掉的规定。规定清单启用了被取代的规定时，构建给出警告，并写出它的后继规定。写在 `rules` 里的规定和 `packs` 里的 pack 根，只有一条后继规定时，用一条命令 `statute upgrade --replace-superseded` 就能在规定清单里把旧 ID 换成新 ID；有好几条规定一起接替它时，这一项留给用户，由用户把它们全部启用，不适用的可以不启用；由别的规定带进来的，警告会写出是哪条规定把它带进来的。启用了已废止的规定，也给出警告。这些都是警告而不是错误，因为规定清单照旧能用。下游用户不必手动顺着取代链往下找。

「升级之前什么都不会变」这个保证只在锁文件留得住旧版本时成立，也就是按 commit 锁定的 git 规定源。磁盘上的规定源没有旧版本可留：锁文件只记每条规定的 SHA-256，规定一改，算出这个哈希的那份文件就没了。所以 `lock` 按磁盘上的规定源现在的样子读，和 uv 对待 path 依赖一样；`upgrade` 写出同样的锁文件，并显示变了什么。也是因为这个，第一版给不出改动的文字：它只列出宪法的修订号、修订号或内容有变动的每条规定，以及被带进来 (附上原因) 或去掉的每条规定。文字 diff 等 git 规定源实现后再做，那时可以读到旧的 commit。规定的原文变了而修订号没变，`lock` 会给出警告，`upgrade` 会在那条规定的那一行注明，因为规定改了，修订号就要加一 ([ID 与修订号](rule-format.md#ids-and-revisions))。这两处比的是去掉译文之后的规定：把规定按 TOML 读进来，去掉 `[translations]` 和原文以外各语言的文字，按键排好序写成 JSON，再算 SHA-256。这样改原文或改别的任何字段都算，只改译文或只改文件的排版都不算。只改了译文的规定不会引起警告，`upgrade` 照样列出它，并注明修订号没变。锁文件若写于开始记这个哈希之前，就改比文件的 SHA-256。

**绑定一部宪法。** 规定清单写明它依据的宪法：来自哪个仓库、哪一版 (edition)、哪个修订号 (revision)。锁文件像固定规定源的提交那样固定这个修订号，一次编译只用一部宪法的一个确切修订号。依据不同宪法的规定清单不会合在一起用：仓库和版至少要一致，修订号则对照每条规定来检查 (见[从规定追溯到宪法](rule-format.md#tracing-rules-to-the-constitution))。宪法修订后，钉在旧修订号上的规定清单不会变；把它移到新修订号上，和别的升级一样是一个明确的步骤。继承了基础规定清单的清单，钉的修订号可以与基础清单不同；这时构建取其中较新的那个，如果有已启用规定的范围容不下它，构建就失败。

**按仓库划分，可以继承。** 规定清单属于一个仓库，它可以继承一份共用的基础规定清单 (写在它的 `base` 字段里，尚未实现)，这样一个用户或团队的所有仓库都认可的规定只写一次。仓库在基础清单之上增加规定、去掉规定，并在 one-of 的子节点中作出选择。这样，当前设计中的法域 (`division-of-instructions.rules`) 就成了一份基础规定清单的所有者，它的各个仓库继承这份清单；每个仓库的规定清单和编译输出，取代每个法域一份的规定选择和编译文件。互斥按规定清单检查，所以一个仓库可以用 uv 管理它的 Python 包，另一个用 Bazel。

**monorepo。** 规定清单可以按路径分成几段，每段指明一个目录和适用于它的规定。互斥在每一段内检查，所以 monorepo 的一部分可以用 uv，另一部分用 Bazel。各个 agent 怎样处理子目录里的指令文件，已在 2026-10-14 测过，只测了非交互模式 (Claude Code 2.1.296、Codex 0.159.3、Grok 1.0.50；Grok 只在受信任的文件夹里加载项目指令)：

- 工作目录在子目录时，三家在启动时都会加载那个子目录的指令文件。
- 工作目录在仓根、要改子目录里的文件时，只有 Claude Code 会自己加载子目录的 `CLAUDE.md`，时机是碰到那里的文件。Codex 和 Grok 什么都不加载，要靠模型自己去读；这次的几轮里模型都读了。Grok 有两轮先读了子目录的文件、后读仓根的文件，两轮遇到冲突都按仓根的办，与它的文档不符。
- 默认情况下，Claude Code 只有在工作目录及其上层都没有 `CLAUDE.md` 时才读 `AGENTS.md` (有设置可以让它两种都读，没有测过)。

所以分段规定不能指望自己目录里的指令文件被读到。编译器把每一段的规定都编译进仓根的指令文件，每条这样的规定写明它适用的目录；同一个仓库的编译输出只用一个文件名。子目录里可以再放一份重复某一段的文件，但不依赖它被读到。

**放在哪里。** 这套设计仿照 uv 这样的包管理器：规定源相当于包索引，规定清单相当于项目 manifest，锁文件就相当于锁文件，编译相当于 sync，用户级缓存相当于包缓存。仓库里放规定清单、锁文件和编译输出；升级是在仓库里执行的一条命令，结果以一个 pull request 的形式出现。用户级只放命令、规定源的缓存，以及很薄的一层个人设置，存放与人有关、与项目无关的内容：回复用什么语言、把消息当作语音转文字来读、凭证存放在哪里、机器上的目录怎样布局。这一层接管设计中已有的私有 overlay 里与个人相关的那部分。每条规定声明一个默认层级 (项目规定在仓库级，关于人或机器的规定在用户级)，用户可以修改。这样做的原因是：克隆仓库的人、CI 和云端的 agent 都读不到用户级的文件，而且每个仓库固定自己的版本，按自己的节奏升级。第一版只做仓库级 ([命令与第一版](statute-command.md#the-command-and-the-first-version))。规定源的缓存，以及为所有仓库登记规定源的全局配置，设计在[全局配置与 git 规定源](global-configuration.md)；个人那一层规定还没有设计。

## <a id="sources-and-references"></a>规定源与引用

一条规定由它的规定源和 ID 确定。提交不属于这个标识的一部分。

**给规定源起名。** 规定清单在 `[sources]` 表里列出每个规定源，并写明地址和要跟随的 tag 或分支：

```toml
[sources]
R = { git = "https://github.com/Luolc/agent-constitution", tag = "<tag>" }
team = { git = "example.test/their-team/rules", branch = "main" }
```

键 `R` 留给第一方规定源，也就是本仓：宪法和通用规定都由它发布。规定清单像声明别的规定源一样声明它，写明要读的 tag、分支或路径；也可以不写，交给全局配置和内置默认，即第一方仓库的 `main` 分支 ([全局配置与 git 规定源](global-configuration.md#the-global-configuration))。其余每个规定源都有一个短名，由小写单词加连字符组成，由规定清单自己起。`L` 和 `local` 留给仓库自己的规定 (见下)；`ac` 是第一方规定源以前的名字，用它会报错，并提示改名为 `R`。规定源也可以是磁盘上的一个目录，`R = { path = "." }`，路径相对于规定清单所在的目录：自己存放规定的仓库，比如本仓，就这样指向自己。它的规定在该目录下的 `rules/` 里，宪法在 `constitution/<edition>/` 里。规定源也可以是一个 git 仓库，克隆到用户的 statute 目录里，按锁文件固定的提交读取 ([git 规定源](global-configuration.md#git-sources))。一个用户的所有规定清单都能用的规定源，以及第一方规定源的默认地址，来自全局配置，规定清单自己的 `[sources]` 按名字覆盖它们 ([一个名字指哪个规定源](global-configuration.md#which-source-a-name-means))；只用到这些规定源的规定清单可以不写 `[sources]`。

**三种引用。** 每种引用各有自己的写法，不会把一种读成另一种：

- 第一方规定：`R` 加 ID，`R42`；
- 本地规定，即规定清单旁边 `rules/` 目录里的规定，也就是存放这份清单的仓库自己的规定：只写 ID，`12`；`L12` 和 `local:12` 意思相同；
- 别的规定源的规定：短名、一个冒号和 ID，`team:7`。

statute 不论在哪里提到一条规定，都用同一种写法：提示信息、`statute explain`、锁文件和编译出的 `AGENTS.md` 里都是 `R42`、`L12` 或 `team:7`。本地规定显示成 `L12`，免得看起来像 `R12`。网站只列第一方规定，写成 `R42`。规定清单里的条目按写进去的样子保留，添加条目的命令写成 `R42`、`12` 或 `team:7`。

第一方规定源就是规定清单所在的目录时，即 `R = { path = "." }`，比如本仓，它的 `rules/` 就是第一方规定。这些规定写成也显示成 `R12`；用本地写法引用其中一条，比如 `12`，会报错并提示写成 `R12`，这样一个文件不会有两个名字。

别的规定源的短名只在定义它的文件内有意义，所以两份规定清单可以用 `team` 指不同的规定源。规定源搬到别的地址时，规定清单改一行，引用一个都不用改。一个规定源如果引用了别的规定源里的规定，它也有自己的 `[sources]` 表，形式相同，其中的名字不必与使用它的任何规定清单一致。构建按地址而不是按名字匹配规定源：一个文件里的 `team` 和另一个文件里的 `core` 指向同一个地址时，就是同一个规定源。

**规定里的引用。** 在一条规定自己的文件里，`requires` 或 `conflicts` 里的数字和正文里的引用 `{@rule:<id>}`，指的都是同一规定源里的规定。要指别的规定源的规定，在 `requires` 或 `conflicts` 里写成 `"R12"` 或 `"team:7"`，在正文里写成 `{@rule:R12}` 或 `{@rule:team:7}`，名字取自本规定源自己的 `[sources]` 表；statute 目前用规定清单里的名字来解析。第一方规定源里的规定引用另一条第一方规定，只写编号；在那里写 `"R12"`，statute 会提示改写成 `12`。编译时，同一规定源的规定加上该规定源的前缀显示：第一方规定里的 `{@rule:12}` 显示为 `R12`，本地规定里的显示为 `L12`。

**版本记在规定源上。** 规定清单写明跟随一个规定源的哪个 tag 或分支；锁文件把它解析到一个确切的提交。这也是 `pyproject.toml` 和 `uv.lock` 的分工：manifest 写明一个范围，锁文件记下确切的版本。引用不带提交，原因有两个。一是升级就得改每一处引用。二是如果同一规定源的两条规定固定在不同的提交上，它们之间的 `requires` 或 `conflicts` 就会指向一条与选用的那条不同的规定。所以一份规定清单对每个规定源只取一个版本。

**跨规定源的依赖。** 一个规定源的规定可以在 `requires` 下列出另一个规定源的规定，例如 `"R12"`。这时依赖方所在的规定源要在自己的 `[sources]` 表里声明，它适用于那个规定源的哪些版本，写成一个用 Python 版本说明符表示的范围。编译时，构建为每个规定源寻找一个被所有声明都接受的版本。规定清单自己跟随的 tag 或分支也算作其中一项声明。找不到这样的版本，构建就失败，并指出相互冲突的声明。

**取代只在规定源内部发生。** 只有规定源自己能取代自己的规定。别的规定源不能声明它的规定替代了我们的规定。它可以在自己规定的正文里推荐这个替代；换不换，由用户在自己的规定清单里决定。

**第三方的规定。** 用户可以启用自己选定的规定源里的规定，比如某个团队自己的规定源，或者别人的公开规定源。这是用户的权利，风险也由用户承担：第三方的规定不经过本仓规定的那套审查，却会左右读取编译结果的 agent。内置规定写明，来自本仓之外的规定源的规定和 skill，启用前要怎样检查。默认情况下，用户用默认的宪法和默认的规定清单，不引入任何第三方规定源。引入第三方规定是高级用法，细节以后再写；宪法里不写这些。

**查找公开的规定。** 这件事不需要有人运营一台中心服务器。可以用一个索引仓库列出已知的公开规定源，就像 Homebrew 列出它的 tap 一样，网站上的完整列表也可以从这个索引构建。这一步放在后面做，不属于第一个版本。

## <a id="dependencies-one-ofs-and-packs"></a>依赖、one-of 与规定包

规定之间有两种关系，树上还有另外两种节点：领域和 one-of。

- `parent`：每条规定恰好有一个 parent，它可以是另一条规定、一个 one-of 或一个领域 (见下文)，所以规定构成一棵树，每个领域逐级细化。覆盖另一个规定源的规定的那条规定没有 parent，它站在被覆盖的那条规定的位置上 (见[覆盖](rule-sources.md#overrides))。这棵树决定一条规定在编译出的文本和网站上的位置、它编译进哪个块，以及它属于哪个规定包。
- `requires`：启用规定 A 需要另一条规定 B，或者一个 one-of (见下文)。一条规定可以依赖好几条，这些依赖构成一个有向无环图。一条说明怎样通过 uv 运行检查的规定，依赖让 uv 管理项目依赖的那条规定。也可以依赖另一个规定源的规定；见[规定源与引用](#sources-and-references)。

只有 parent 不够，因为许多规定横跨几个领域：「在 CI 里先运行 `uv sync --locked`」既依赖 uv，也依赖 CI 服务。它放在 uv 那条规定下面，并依赖 one-of「CI 服务」，这个 one-of 的任何一个子节点 (例如一条关于 GitHub Actions 的规定) 都能满足它。

**领域。** 领域是树顶层的节点，例如 Python、CI、Git 或安全。除了 ID 和标题，它只有每个节点都有的那几个字段，以及可选的 applicability，用一两句话说明它适用于哪些仓库 ([规定文件格式](rule-format.md#rule-file-format))，没有正文和检查；它不能单独启用。它下面有任何一条规定启用时，它就作为标题出现在编译输出里。一个领域可以挂在一个没有 parent 的领域下面，成为子领域，所以领域最多嵌套两级 (见[子领域](rule-sources.md#subdomains))；更细的分组用领域下面的规定或 one-of。

**one-of。** one-of 是 parent 树上的一种节点，在一份规定清单 (或者它的一个路径分段) 里，它的子节点至多启用一个。一个都不启用也可以，比如完全不用 Python 的仓库；这里的 one-of 从不表示「恰好一个」。Python 下的 one-of「Python 包管理器」有 uv、Poetry 和 Bazel 三个子节点。one-of 有 ID，增加一个 one-of 和增加一条规定一样要经过审查。依赖 one-of 的规定，只要它的任何一个子节点启用，就算满足。实现之后，每个 one-of 都指定一个默认子节点，规定清单没有点名子节点时，规定包和依赖都取这个默认子节点，而不是像下文那样不产生内容或报错 ([one-of 的默认](rule-config.md#in-the-rule-files))。

**后来才发现的冲突。** 没人当作备选项的两条规定，可能后来发现不能一起用。怀疑这一点的 agent 报告它，由审查方判断。通常的解决办法是修改规定：拆分、收窄或者改写措辞，保不保留 ID，见[ID 与修订号](rule-format.md#ids-and-revisions)。两条规定都没有问题、只是不能一起用时，在其中一条上写 `conflicts = [ID]`。这个关系是对称的，只写在一边：写在后来的那条上，即发现冲突时正在新增或修改的那条，从不改动早已存在的那条。跨规定源时本来也只能写在自己这边。另一边由命令反推出来，构建检查和网站都在两条规定上显示这个冲突。两边都写了，给一个警告，不算错误。理由是：同一个事实只写在一处 (`no-restating`)，而别的规定源的文件改不了。同一位置上三条或更多互相冲突的规定是备选项，改为收进一个 one-of。一条规定不得声明与这样的规定冲突：启用它时会沿着 `parent` 或 `requires` 直接或间接带进来的规定，因为启用前者就会启用后者；构建遇到这种声明会失败。同一个 parent 下的兄弟规定可以互相冲突。

构建检查下面这些约束：

- 树里和依赖里都没有环，同一规定源内没有，跨规定源也没有。
- 领域没有 parent，或者作为子领域，以一个没有 parent 的领域为 parent；每条规定和每个 one-of 都有 parent，带 `overrides` 的规定除外。
- 规定的 parent 是规定时，算作它的一项依赖：启用一条规定就要求启用它的 parent，parent 不在 `requires` 下重复写。parent 是 one-of 时，这项依赖穿过 one-of，落到 one-of 自己的 parent 上：启用「Python 包管理器」下的 uv，仍然要求启用这个 one-of 上面的那条规定。parent 是领域时不产生依赖。one-of 的某个子节点启用了，就算这个 one-of 启用了。
- 没有多余的依赖：如果 A 依赖 B、B 依赖 C，A 就不再列出 C。
- 跨到另一棵子树的依赖，应当指向一个 one-of，而不是某条具体的规定。这类依赖的数量没有硬性上限；构建会对它们给出警告。
- 在一份规定清单或一个路径分段里，一个 one-of 至多启用一个子节点，启用的规定之间没有冲突。一条规定沿着 `parent` 或 `requires` 会带进同一个 one-of 的两个子节点的，永远无法启用，构建遇到它会失败；依赖一个还没有子节点的 one-of 的规定也一样。
- 一条规定依赖已被取代或已废止的规定时，给出警告，有后继规定的写出全部后继规定。

**缺的依赖自动补上。** 规定清单启用了一条规定、却没有启用它依赖的某条规定时，statute 像包管理器补依赖那样补上缺的那条：规定清单只列直接选用的规定，锁文件记下带进来的规定，升级的 diff 里能看到它们。算作依赖的 parent 也一样处理。在缺依赖的各种情形里，唯一失败的是依赖指向一个 one-of，而规定清单一个子节点都没有启用：statute 不能替用户选，于是失败，并列出可选的子节点。

规定包：一个规定包就是一棵子树，以它的根命名，规定清单把根写进 `packs`，就能整个启用它。规定包里的 one-of，规定清单没有为它指定子节点的，和任何一个子节点都没启用的 one-of 一样，不产生任何内容；只有某条启用的规定依赖这个 one-of 时，构建才按上文失败。规定清单在 `rules` 里指定了子节点的，规定包就继续延伸到那个子节点的子树。第一版里，这是进入 one-of 的唯一途径：只因为被某条规定依赖而启用的子节点，不会让规定包延伸到它的子树；作为 one-of 子节点的 one-of，规定包永远进不去。规定包里被取代或已废止的规定不启用，它下面的规定也一样；规定包的根本身被取代或已废止时，这个规定包什么也不启用，构建给出警告，和 `rules` 里写了这样的规定时一样。
